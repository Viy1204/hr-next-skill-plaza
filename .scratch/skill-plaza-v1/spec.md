# HR NEXT 技能广场 v1

Status: ready-for-agent

## Problem Statement

HR NEXT 是一个跨公司的 HR 社群。社群里有两件事一直做不起来：

1. **个人做出来的能力散落在个人手里。** 成员各自写了能用的 HR 技能（招聘寻源、花名册、组织架构图、考勤分析等），但只能靠在群里贴链接分发。没人知道有哪些、哪个好用、要什么前置条件才能跑起来，也没有任何"哪个最受欢迎"的信号。想找一个技能的人翻不到，做出技能的人也拿不到反馈。
2. **想要能力的人和能做能力的人对不上。** 群友天天在群里说痛点（"每个月核对花名册要花一整天"），这些话滚过去就没了。既没有沉淀的地方，也没有机制让有空的人看到"有 10 个人都在等这个东西"从而愿意动手。

社群主的意图是不商业化、把模块分给大家；参与者对时间的承诺是"尽量参与"。所以任何依赖单个人持续运维、或依赖一套只有开发者能改的后台的方案，都会在两个月内停摆。

## Solution

一个部署在公网、链接只在 HR NEXT 飞书群内分发的网页，两块内容：

**技能广场** —— 可浏览、可按适用职能筛选、可搜索的技能目录。每个技能条目说明它能干什么、属于哪个技能包、需要什么前置条件。点「取得」走平台的统一出口，平台记一次取得数再把人送到文件或仓库。技能包按取得数排序，社群第一次拥有"哪个能力最被需要"的公开信号。

**许愿池** —— 任何人可以提一条许愿，只描述痛点场景，不需要想技术方案。别人看到"我也有这个痛点"就点附议。附议数是唯一排序依据。一条许愿的附议数达到阈值，自动升级为待认领任务并推到群里招人。有人做出来之后，把技能包关联到这条许愿上，许愿就算交付了。

两块互相导流：看完技能包可以顺手许愿"我想要类似的但……"；技能包页面反向标出"源于这条许愿"。

数据存在飞书多维表格里，运营和群主可以直接改数据、加字段、建视图，不必找开发。新许愿、附议达阈值、技能包交付三类事件由群自定义机器人推回群里 —— 群是唯一的触达通道，网页只是货架。

## User Stories

### 浏览与发现

1. 作为社群成员，我想在手机上从群里点开链接就能正常浏览全部内容，因为链接只在飞书群内分发，绝大多数人是在手机上打开的。
2. 作为社群成员，我想看到一个技能条目列表，以便知道社群里现在到底有哪些能力。
3. 作为社群成员，我想按适用职能筛选技能条目，以便只看跟我岗位相关的那些。
4. 作为社群成员，我想按关键词搜索技能条目的名称和说明，以便直接找到"考勤"或"花名册"相关的能力。
5. 作为社群成员，我想看到技能包按取得数从高到低排序，以便优先看别人试过最多的。
6. 作为社群成员，我想在每个技能条目上看到它属于哪个技能包，以便知道我取得的是一个单独能力还是一整套。
7. 作为社群成员，我想在技能包详情页看到它包含的全部技能条目，以便判断这一整包值不值得装。
8. 作为社群成员，我想在取得之前就看到前置条件（运行时、浏览器、平台登录态、API 凭证），以便判断我这台电脑到底跑不跑得起来，而不是装完才发现缺东西。
9. 作为社群成员，我想在页面上看到取得数被明确标注为"有人想试"而不是"有多少人在用"，以便不把它误当成质量证明。
10. 作为社群成员，我想看到技能包的提报人昵称，以便知道这是谁做的、在群里找谁问。
11. 作为社群成员，我想在技能包详情页看到它"源于哪条许愿"（如果有），以便看到社群共创真的走通过一次。

### 取得

12. 作为社群成员，我想点一个「取得」按钮就拿到技能包，无论它是自托管 zip 还是 GitHub 仓库，以便我不用关心它托管在哪。
13. 作为社群成员，当技能包是 GitHub 仓库时，我想被送到那个仓库页面，以便按作者的 README 安装。
14. 作为社群成员，当技能包是自托管 zip 时，我想直接下载到文件，以便离线安装。
15. 作为社群成员，我想在计数服务出问题时依然能成功取得技能包，因为我要的是文件，不是那个数字。
16. 作为社群运营，我想同一个人反复点取得不会把取得数刷上去，以便排序还有参考价值。
17. 作为技能包提报人，我想我的技能包被取得后取得数会增加，以便我看到自己的东西有人试。

### 许愿

18. 作为有痛点的社群成员，我想不注册不登录就能提一条许愿，以便我不会在门口就放弃。
19. 作为许愿人，我想按"谁、在什么时间、进行什么操作、需交付什么结果"的结构描述痛点，以便认领人看得懂我到底卡在哪。
20. 作为许愿人，我想只描述痛点而不必设计技术方案，以便我不会因为想不出方案就不提了。
21. 作为许愿人，我想给许愿选一个适用职能，以便对应职能的人能筛到它。
22. 作为许愿人，我想选填"我每月为这件事花多少小时"，以便认领人判断这事值不值得做。
23. 作为许愿人，我想这个工时数字不进入任何排序公式，以便我不用担心填小了就没人看、也不用被迫编一个大数字。
24. 作为许愿人，我想提交后立刻能在许愿池里看到我的许愿，以便我确认提交成功了。
25. 作为许愿人，我想留一个昵称署名，以便群友知道是我提的、可以来找我聊细节。
26. 作为社群成员，我想在群里收到"有人提了新许愿"的推送，以便我不用天天刷网页。

### 附议

27. 作为社群成员，我想给某条许愿点附议表示"我也有这个痛点"，以便让它排到前面去。
28. 作为社群成员，我想看到附议按钮的文案是"我也有这个痛点"而不是"点赞"，以便我不会把它当成"这想法不错"随手点。
29. 作为社群成员，我想看到许愿池按附议数从高到低排序，以便一眼看到最多人卡的是哪件事。
30. 作为社群成员，我想按适用职能筛选许愿，以便只看我这个模块的痛点。
31. 作为社群运营，我想同一个人对同一条许愿只能附议一次，以便附议数还能当排序依据。
32. 作为社群成员，我想在附议成功后立刻看到附议数变化，以便我确认点上了。

### 待认领任务与认领

33. 作为社群运营，我想一条许愿的附议数达到阈值后自动升级为待认领任务，以便附议排序真的触发一次招募动作而不只是改变展示顺序。
34. 作为社群运营，我想阈值是一个可改的配置项，以便上线后看真实分布再调，不用改代码发版。
35. 作为社群成员，我想在群里收到"这条许愿已有 N 人附议，开放认领"的推送，以便我有空的时候能接。
36. 作为想动手的社群成员，我想认领一条许愿，以便让许愿人知道有人在做了。
37. 作为想动手的社群成员，我想在别人已经认领的许愿上也能认领，以便我不会因为被人占了位就不做了。
38. 作为许愿人，我想看到"N 人在做"，以便我知道这事有人接了。
39. 作为社群成员，我想看到认领人的昵称和一句说明，以便我能在群里找他一起做。
40. 作为社群成员，我想理解认领只是软意向不是承诺，以便认领没交付时不会有人被追责、也不会有人因为怕失信而不敢认领。

### 交付

41. 作为技能包提报人，我想把技能包关联到一条许愿上，以便这条许愿被标记为已交付。
42. 作为社群成员，我想看到一条许愿是由哪个技能包交付的，以便我直接去取得它。
43. 作为社群成员，我想在群里收到"某条许愿已交付"的推送，以便我知道这个池子真的能出东西。
44. 作为社群运营，我想许愿的交付状态由"是否有技能包关联到它"决定，而不是由认领决定，以便状态永远反映真实产出。

### 审核与内容安全

45. 作为社群运营，我想技能包在人工审核通过前对外不可见，因为技能包一旦被取得就无法召回，事后下架删不掉已有副本。
46. 作为社群运营，我想许愿和附议无需审核直接可见，因为它们可改可删，而审核队列会掐死冷启动期的参与量。
47. 作为社群运营，我想在多维表格里改一个字段就能让技能包上架或下架，以便我不需要一个专门的管理后台，也不需要找开发。
48. 作为技能包提报人，我想在提报时必须勾选脱敏声明（不含真实员工数据、薪酬明细及所属公司未公开资料），以便我在上传前先想清楚这份东西能不能拿出公司。
49. 作为社群成员，我想一条被下架的技能包不再出现在列表和详情里，以便我不会取得已被判定有问题的东西。

### 运营与数据自治

50. 作为社群运营，我想直接在多维表格里增删改所有数据，以便运营节奏不被开发者的响应速度卡住。
51. 作为社群运营，我想在多维表格里改推送文案相关的配置，以便调整语气不用发版。
52. 作为社群运营，我想群推送只推三类事件（新许愿、附议达阈值、技能包交付），以便群里不被通知淹没。
53. 作为群主，我想整套东西（租户、表、应用、域名、部署）能迁到我名下，以便社群不依赖某一个人。

## Implementation Decisions

### 架构与边界

- 前台是一个部署在 Vercel 的 Next.js 应用；数据存在飞书多维表格。见 ADR-0002。
- **不做飞书 ID 登录**。飞书自建应用是单租户的，跨租户要走 ISV 上架，成本与周期都不成立。见 ADR-0001。
- v1 无登录、无账号体系。链接只在 HR NEXT 飞书群内分发，"你已在群里"就是身份。
- **"人"不聚合**。昵称只是一个字符串字段，不做任何跨记录归并，不做贡献者榜、不做个人中心。未来接真身份时靠人工认领迁移。
- 移动优先。分发渠道是飞书群，主要访问设备是手机。
- 全部飞书出站调用收在两个 port 后面：**多维表格读写 port** 与 **群通知 port**。应用其余部分不直接触碰飞书 SDK 或 HTTP。这是系统唯一的测试 seam。

### 数据模型

六张多维表格。（这是对早期"四张表"草图的修正：附议与认领形状不同 —— 附议是高频匿名计数，认领带昵称和说明 —— 合表会让两边都别扭。配置独立成表是为了让运营能改阈值。）

1. **技能包** —— 名称、简介、载体类型（`zip` | `github`）、取得地址（zip 附件或仓库 URL）、前置条件、提报人昵称、审核状态（`待审` | `已发布` | `已下架`）、取得数、关联许愿、创建时间
2. **技能条目** —— 名称、说明、所属技能包、适用职能、展示顺序
3. **许愿** —— 标题、痛点场景、适用职能、痛点工时（选填）、许愿人昵称、附议数、状态（`收集中` | `待认领` | `已交付`）、创建时间
4. **附议** —— 关联许愿、去重标识、创建时间
5. **认领** —— 关联许愿、认领人昵称、说明、创建时间
6. **配置** —— 单行表，含附议升级阈值（初始 10）与推送文案

字段级约定：

- 取得数是技能包上的计数字段，**不摊到技能条目**。取得数只在技能包之间可比。见 ADR-0006。
- 附议数存在许愿上作为可读计数，附议表是明细。
- `适用职能` 是技能条目与许愿共用的唯一分类维度，取值：招聘 / 组织与人才发展 / 薪酬福利 / 绩效 / 培训 / 员工关系 / HR 数据分析 / HR 运营与共享服务。**不做**第二个分类维度。
- 许愿状态由数据推导而非手工维护：有技能包关联 → `已交付`；附议数 ≥ 阈值 → `待认领`；否则 `收集中`。

### 对外接口

- `GET /` —— 首页，两块入口 + 各自的头部内容
- `GET /skills` —— 技能条目列表；支持适用职能筛选与关键词搜索（匹配条目名称与说明）；默认按所属技能包取得数降序
- `GET /skills/:packageId` —— 技能包详情：简介、前置条件、包含的技能条目、取得按钮、来源许愿（如有）
- `GET /get/:packageId` —— **取得统一出口**。先记一次取得，再按载体类型 302 到仓库 URL 或下发 zip。GitHub 载体的裸链不在页面上暴露，一律经此出口。见 ADR-0002 的计数点约定
- `GET /wishes` —— 许愿池列表；按附议数降序；支持适用职能筛选
- `GET /wishes/:id` —— 许愿详情：痛点场景、痛点工时、附议数、认领人列表、交付的技能包（如有）
- `POST /wishes` —— 新建许愿，立即可见，触发「新许愿」推送
- `POST /wishes/:id/endorse` —— 附议；同一去重标识对同一许愿幂等；跨过阈值时升级状态并触发「开放认领」推送
- `POST /wishes/:id/claim` —— 认领；不排他；**不触发推送**

### 关键行为约定

- **取得永不被计数拖垮**：先尝试记数，失败只记日志，302 / 下发照常发生。取得数是最终一致的参考值，不是账。见 ADR-0002。
- **取得数去重**：服务端下发一个匿名 httpOnly cookie 标识，同一标识对同一技能包在 24 小时内只计一次；无 cookie 时回落到 IP。该标识**仅用于去重**，不写入任何可读字段、不参与聚合、不对外展示。
- **附议去重**：同上标识，同一许愿只计一次；重复附议返回成功（幂等），不报错、不重复计数。
- **审核过滤在读取层**：`已发布` 之外的技能包不出现在任何列表、搜索结果与详情页。审核动作发生在多维表格里，不做管理后台。
- **阈值升级是提交路径上的同步动作**：附议写入后立即判定是否跨过阈值，跨过则改状态并发推送。不用定时任务。
- **群通知只出站**，用群自定义机器人 webhook。**明确不监听群消息**。见 ADR-0007。
- **v1 不做技能包上传流**。首批 12 个技能条目（`Viy1204/hr-skills` 5 包 5 条目、`Viy1204/recruiting-copilot` 1 包 7 条目）由人工录入多维表格。
- 认领是软意向，无排他锁、无超时释放。**不要为它加锁** —— 无登录下锁不住，且在志愿社群里只会产生僵尸认领。见 ADR-0003。

### 术语

界面文案与代码标识一律使用 `CONTEXT.md` 的术语：技能包、技能条目、前置条件、取得数、许愿、附议、痛点工时、待认领任务、认领、交付、适用职能。特别地：界面上**不出现**"下载量""使用量""点赞""开放认领"这些被 `_Avoid_` 掉的词。

## Testing Decisions

### 什么算好测试

只测对外可观察的行为，不测实现细节：HTTP 响应状态与跳转目标、列表/详情里看得见看不见什么、页面上显示的计数值、群里收到的消息内容。**不断言**多维表格的表结构、字段名、调用次数与调用顺序。重构存储布局或换掉多维表格时，这批测试不应该跟着改。

### seam

唯一 seam 是**飞书出站边界**，两个 port：多维表格读写、群通知发送。测试提供内存实现（一个可预置数据的假表、一个把消息收进数组的假通知器），从 HTTP 入口打进去，中间全跑真实代码。飞书 SDK 与 wire 格式不进入任何测试。

### prior art

这是空仓库，**没有现存 seam 可复用** —— 这批测试就是后续的 prior art。第一个测试文件要写成模板：一个建立测试应用实例并注入两个假 port 的工厂函数，其余测试全部复用它。不允许出现第二种搭测试环境的方式。

### 要覆盖的行为

取得：

- GitHub 载体的技能包，取得出口 302 到仓库 URL
- zip 载体的技能包，取得出口下发文件
- 取得一次后，详情页上的取得数 +1
- 同一标识 24 小时内重复取得，取得数不变
- 假多维表格写入抛错时，取得依然成功（302 / 下发照常）

目录与审核：

- `待审` 与 `已下架` 的技能包不出现在列表、搜索结果、详情页
- 按适用职能筛选只返回该职能的技能条目
- 关键词搜索匹配技能条目的名称与说明
- 技能条目列表按所属技能包的取得数降序
- 同一技能包下多个技能条目，取得数在每个条目上显示为同一个值（不摊分）

许愿与附议：

- 新建许愿后立即出现在许愿池列表里
- 新建许愿触发一条「新许愿」群消息，内容含许愿标题
- 许愿池按附议数降序
- 附议后附议数 +1
- 同一标识对同一许愿重复附议：返回成功，附议数不变
- 附议数跨过阈值：许愿状态变为 `待认领`，且发出一条「开放认领」群消息
- 附议数达到阈值后继续附议：不重复发送升级消息
- 阈值来自配置：把配置改成 3，第 3 次附议就触发升级

认领与交付：

- 同一条许愿可被多人认领，全部认领人都显示出来
- 认领**不**发送群消息
- 技能包关联到许愿后，该许愿状态为 `已交付`，且详情页给出该技能包的入口
- 交付触发一条「已交付」群消息
- 一条许愿即使无人认领，也能因为有技能包关联而变成 `已交付`

## Out of Scope

- **飞书 ID 登录 / ISV 商店应用上架**。跨租户不成立，见 ADR-0001。
- **账号体系、个人中心、贡献者榜、等级标签**。v1 不聚合"人"。
- **使用数**。平台测不到技能包是否真的在 agent 里跑起来过，不做假指标。
- **技能包上传流与作者自助提报**。v1 人工录入。
- **管理后台**。审核与运营动作在多维表格里完成。
- **监听群消息、AI 从群聊里自动生成候选许愿**。需要自建应用与事件订阅，且有隐私问题，见 ADR-0007。
- **飞书交互卡片与卡片回调**。
- **定期扒 GitHub / skills.sh 热榜推群**。已确认为后续联动项，不在 v1。
- **迁移到群主租户**。独立任务，见 ADR-0005；v1 先建在开发者租户。
- **许愿种子内容的录入**。需要翻群历史并征得原话人同意，只能由社群成员本人完成。
- **任何与激励、奖金、评选挂钩的机制**。见下。
- 第二个分类维度（HRAS 那种「适用场景」）。12 个条目配一个维度足够。

## Further Notes

**取得数与附议数都是可刷的参考值。** v1 无登录，去重只能靠 cookie 与 IP。因此这两个数字不能作为任何激励、奖金或评选的依据 —— HRAS 敢把数据接到大赛激励，是因为它背后有真实的飞书身份，本项目没有。这条限制要在上线前跟群主讲清楚，否则社群一旦想搞评奖会直接撞上来。

**阈值 10 在百人社群里可能永远触发不了。** 附议 10 条约等于全群 10% 的人主动点同一条。而阈值升级是让附议排序真正产生作用的唯一出口，空转就等于这套机制没上线。所以阈值必须是配置项，上线两周后看真实分布再调；做好调到 3 的准备。

**冷启动是最大的产品风险，而它不是技术问题。** 技能目录靠首批 12 个真实条目撑住首屏，许愿池要靠从群历史里捞出来的真痛点、署真名（需先征得原话人同意）。空的许愿池 + 全 0 附议会让第一批访客判断"这儿没人"，而社群产品只有一次首次印象。

**命名。** 产品名定为「HR NEXT 技能广场」。注意「技能广场」恰是参照项目 HRAS AI 岛的模块名，且含义偏窄 —— 许愿池挂在"广场"底下略勉强，将来社群可能会问许愿池算不算技能广场的一部分。已知情选择。

**参照项目的关键差异。** HRAS AI 岛是同一家公司的内部系统（单租户 + 内网 + 雇主 ROI + 大赛激励 + AI 应用小组排期）。它的飞书登录、`月均节省总工时 × 地区人力成本系数 × 复用价值系数` 价值计分、准工作分配式的开放认领，三样都建立在本项目不存在的前提上，全部不可照搬。可以照搬的只有：先做许愿池再长社区的路径、群作为主分发通道、以及"定期扒 GitHub 热榜发群"这种运营招。
