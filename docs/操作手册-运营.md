## 一、审核别人自助提交的技能包（日常主要工作）

作者在网站上自己填表提交（https://viy1204.me/skills/new ），提交的东西**自动落成「待审」，在网站上完全不可见**。你要做的只有一件事：核对，然后把审核状态改成「已发布」。

**怎么找到待审的**：在「技能包」表按「审核状态 = 待审」筛一下，或者建一个叫「待审」的视图常驻。

**核对什么**：

| 看什么 | 不合格怎么办 |
|---|---|
| 取得地址点得开吗、是不是那个项目 | 打不开就别发布，去群里问作者 |
| **前置条件写清楚了吗** | 只写「需要 Node」这种，让作者补具体版本和要自己登录的平台 |
| 简介说清干什么了吗 | 你可以直接改，不用等作者 |
| 技能条目的适用职能选对了吗 | 直接改 |
| 有没有该拆开的 | 几个能各自独立取得的能力塞进了一个包，让作者拆成多个包重提 |

核对完把**审核状态改成「已发布」**，网站上立刻出现。不合适就留在「待审」或改「已下架」，不用删。

作者如果勾了「它交付了哪条许愿」，那条关联已经写在「交付的许愿」字段里了 —— **你发布之后**它才算数（同步跑完那条许愿变「已交付」并推群）。所以别在没核对前就发布。

## 二、自己手工上架一个技能包

作者懒得填表、或者你要补录历史技能包时用。分两步，**两步都做完才会出现在网站上**。

### 第 1 步：在「技能包」表加一行

| 字段 | 怎么填 | 必填 |
|---|---|---|
| 名称 | 技能包名，如 `feishu-roster` | ✅ |
| 简介 | 一两句说清它干什么 | ✅ |
| 载体类型 | `github` 或 `zip` | ✅ |
| 取得地址 | GitHub 仓库 URL 或文件直链 | ✅ |
| 前置条件 | 使用者必须自备的东西：运行时、浏览器、平台登录态、API 凭证 | ✅ |
| 提报人昵称 | 谁做的 | |
| 审核状态 | 新行默认 `待审`，**改成 `已发布` 才会出现在网站上** | ✅ |
| 取得数 | 网站自动累加，**不要手填** | |
| 交付的许愿 | 见下面「交付」一节 | |

**前置条件是必填，不是走过场。** 成员取回去装不上，绝大多数是前置条件没写清楚。写具体版本、具体凭证、具体要自己登录哪个平台。

### 第 2 步：在「技能条目」表加条目

一个技能包至少要有一个条目，否则**它在目录里根本不显示**（目录展示的单位是条目，不是包）。

| 字段 | 怎么填 |
|---|---|
| 名称 | 具体能力名 |
| 说明 | 这个能力做什么 |
| **所属技能包** | **关联到第 1 步那一行 —— 漏了这个条目就不会显示** |
| 适用职能 | 选一个 HR 职能模块 |
| 展示顺序 | 同一个包内的排序，数字小的在前 |

**一个包几个条目？** 看能不能拆开单独用：

- 能各自独立取得（比如 `feishu-roster`、`boss-cli`）→ 各自一个包，一个条目
- 共用一套安装脚本和工作区、拆不开（比如招聘那套 7 个命令）→ **一个包，七个条目**

因为**取得数只挂在包上**，条目不能单独取得。

### 检查

打开 https://viy1204.me/skills ，新条目应该在列表里。**没出现就查这三样**：审核状态是不是 `已发布`、条目有没有关联所属技能包、包的名称有没有填。

## 四、交付：把技能包关联到许愿

**这是许愿被满足的唯一判定依据，跟有没有人认领无关。**

做法：在「技能包」表找到那一行，在**「交付的许愿」**字段关联对应的许愿记录。

关联之后会发生两件事：

1. 那条许愿的状态变成 `已交付`
2. 群里推送一条「✅ 许愿已交付」

⚠️ **但这两件事最多会晚 10 分钟。** 交付发生在表里，网站的请求链路看不见，靠服务器上一个每 10 分钟跑一次的定时任务去比对。

所以你只管在表里关联，别的不用做。**关联完立刻刷新网站，那条许愿可能还显示旧状态 —— 不是坏了，是还没到下一次同步。** 等十分钟再看。

## 五、配置：阈值和群推送文案

在「配置」表改，改完立刻生效。

| 配置项 | 现在的值 | 什么意思 |
|---|---|---|
| 附议升级阈值 | `10` | 许愿攒够这么多附议，自动升级为待认领任务并推群 |
| 取得去重窗口小时 | `24` | 同一个人对同一个技能包，这段时间内只算一次取得 |
| 推送文案-新许愿 | 见表 | 有人提许愿时推的话 |
| 推送文案-开放认领 | 见表 | 附议到阈值时推的话 |
| 推送文案-已交付 | 见表 | 交付关联同步后推的话 |

### 阈值怎么调

初始 10 是拍的。**百人社群里大概率触发不了** —— 上线两周后看真实分布：如果最高的许愿才三四个附议，就把阈值调到 3。宁可早点把人招起来，也别让许愿池死在「没人达标」上。

### 改推送文案要注意两件事

**1. 占位符用 `{字段名}`**，会被替换成真实内容。可用的：

- `推送文案-新许愿`：`{标题}` `{适用职能}` `{许愿人昵称}` `{链接}`
- `推送文案-开放认领`（升级为待认领任务时推的那条）：`{附议数}` `{标题}` `{链接}`
- `推送文案-已交付`：`{标题}` `{技能包名称}` `{链接}`

**2. 文案里必须至少包含这三个词之一：`许愿`、`痛点`、`技能包`。**

群机器人开了「自定义关键词」校验，**不含关键词的消息会被飞书直接拒收，而且网站这边看不出任何异常** —— 你以为推了，其实群里什么都没有。改完文案自己在群里确认一眼。

## 六、绝对不要做的事

这几条会**直接让网站报错或数据错乱**：

| 不要 | 为什么 |
|---|---|
| **改字段名**（中文列名） | 代码按中文列名读数据。把「取得数」改成「取得次数」，那一列立刻读不到 |
| **删表、删列** | 同上，且不可逆 |
| **手动改「取得数」「附议数」** | 网站自动维护。手改会被下一次自动写入覆盖，中间还可能对不上 |
| **手动改「附议」表** | 那是去重记录，改了会导致同一个人能重复附议 |
| **改「适用职能」的选项** | 八个职能模块是代码里写死的固定集合，加了新选项网站认不出来 |
| **把这个 Base 搬到别的租户** | 网站认的是 Base token 和 table id，搬了就断连，要改配置重启 |

想加字段、加视图、加筛选、做仪表盘 —— **随便加，不影响网站**。网站只读它认识的那几列。

## 七、日常怎么盯

**每天扫一眼**：

- 「技能包」表有没有 `待审` 的新行（作者自助提交的）—— 这是唯一会卡住别人的队列，别让它积压
- 「许愿」表有没有新行，内容合不合适

**每周看一眼**：

- 附议数最高的几条许愿有没有人认领；没人认的可以在群里点名喊一声
- 有没有认领了很久没交付的 —— 认领本来就不排他、不是承诺，但可以问问卡在哪，说不定拆开有人能接
- 技能包的取得数分布

**上线两周后做一次**：看附议分布，决定阈值调不调。

## 八、两条底线

**1. 取得数和附议数不能作为激励依据。**

站点没有登录，这两个数都是可以刷的参考值。它们只用来帮大家决定「先试什么、先做什么」，**不得用于奖金、评选、绩效或任何形式的排名激励**。这一点要跟群主讲清楚 —— 一旦挂上利益，数字立刻失真，池子也就废了。

**2. 「取得数」不代表好用。**

它只代表有人想试。前置条件不满足的技能包，取回去大概率装不上。别把高取得数当成质量背书往群里推。
