# 前台部署在社群服务器上，不用 Vercel

[ADR-0002](./0002-bitable-as-datastore-vercel-as-frontend.md) 选了 Vercel 作前台，并预留了「后续迁到自有服务器」的后路。这条把那个后路提前用掉：v1 就直接部署在服务器上，Vercel 不再是目标。数据层不变，多维表格仍是唯一存储。

改的理由只有一个：**链接是在飞书群里用手机点开的**。`*.vercel.app` 在国内基本连不上，自定义域名指向 Vercel 也经常慢和丢包。给一群国内 HR 发一个打不开的链接，等于没上线。Vercel 的免费额度和零运维在这条面前不值一提。

当前落点是社群测试账号名下的一台腾讯云机器（首尔，2 vCPU / 1.9G），对外地址 https://viy1204.me。首尔是境外机房，所以域名不需要备案。入口是 Caddy（80/443，Let's Encrypt 自动签发续期），应用只听 `127.0.0.1:3000`，公网碰不到 Node 进程本身。`www` 永久跳转到 apex，站内链接与群推送一律用 apex —— 两个地址各自被收藏、被分享，日后换域名要改的地方就翻倍。

形态是 systemd + Next standalone 产物，不是 Docker。ADR-0002 写的是 Docker，但那台机器上还跑着别的服务，可用内存只剩五百来兆：Docker daemon 本身要吃掉一两百兆，而 `next build` 峰值超过 1G，在上面构建必 OOM。所以构建一律在开发机或 CI 完成，服务器只解包产物、重启服务（`scripts/deploy.sh`）。换机器时重跑同一个脚本即可，迁移成本并不比镜像高。

代价：没有 Vercel 那种 push 即部署和自动回滚，得自己维护 Node、证书和进程；单机没有冗余，机器挂了站点就没了。对一个社群小站，这个代价小于「国内打不开」。

**这台服务器目前挂在开发者名下，与 [ADR-0005](./0005-community-owns-the-tenant-and-deployment.md) 冲突**，属于明知故犯的过渡状态：先让社群能用上，别为等资源推迟上线（ADR-0002 的原话）。社群那台服务器和域名到位后必须搬走，搬之前这条不算了结。
